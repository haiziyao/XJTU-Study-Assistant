## 三、架构与对外契约（实现必须照这个来）

### 3.1 记忆模块（`app/src/modules/memory/`）
AI 侧**已经预留**调用点（`ai/chat-service.js:359`），必须实现这个签名：

```js
memory.inject({ view, module, courseId, maxItems, maxChars })
// → { injected: [{ text, ... }], truncated: boolean }
// 默认预算 maxItems: 8 / maxChars: 600（ai/chat-service.js:32 DEFAULT_MEMORY_BUDGET）
```

- `inject` **只读、不抛异常、失败降级为空**（记忆坏了不能让对话不可用）。
- 预算要真生效：按分数排序后逐条累计字数，超了就截断并 `truncated: true`（整条进或不进）。
- 一条记忆 ≤ 200 字；「模型只能提议、用户确认才落库」（见接口文档 §10）。

### 3.2 会话生命周期（`ai/routes.js`）
- 已有：`GET/POST /ai/conversations`、`GET/DELETE /ai/conversations/:id`、`DELETE /ai/conversations`（清空）。
- 新增：`PATCH /ai/conversations/:id`（`title` ≤200 字 / `archived` / `pinned`），`GET /ai/conversations?archived=0|1|all`（默认 0），置顶在前、其余按更新时间倒序。
- 归档 = 不删除、可恢复；`DELETE` 才是真删除。

### 3.3 定时唤醒（`ai/schedule.js`）
一条任务：`id / label / prompt(≤2000) / at('HH:MM' 或 ISO) / repeat(daily|weekly|once) / weekdays / enabled / lastRunAt / nextRunAt / conversationId / lastError`。
纯函数 `computeNextRun(task, now)` + `dueTasks(now)` + `markRun(...)`（可测、幂等）；定时器最多每分钟检查一次，**runner 可注入**，未注入时只记录不执行。
路由：`GET/POST /ai/schedules`、`PATCH/DELETE /ai/schedules/:id`、`POST /ai/schedules/:id/run`（「现在试一下」）。

### 3.4 联网搜索（`ai/web-search.js`）
```js
searchWeb({ query, mode: 'web'|'campus', limit, config, fetchImpl, log })   // → [{title,url,snippet,source}]
readPages(results, { limit, fetchImpl, concurrency, maxChars })             // → [{title,url,ok,text,error}]
detectCampusNetwork({ fetchImpl })                                          // → 探测结果 + 理由
```
- provider 选择：有 key → API；无 key → 解析 Bing/百度结果页；**反爬时返回空并说明原因，绝不假装搜到**。
- 正文每页截断约 4000 字、并发 3–4、单页失败用 `ok:false` 标记。
- AI 工具 `web_search`（`mutates:false`），回答里必须引用真实 URL。

### 3.5 外壳给视图的能力（`renderer/shell/app.js`）
`window.PCModules.service('chat', ...)` 暴露：`openConversation(id)`（把历史对话加载进左侧聊天框）、`newConversation()`、`currentId()`、`sendMessage(text)` —— 新视图靠它驱动聊天栏，不自己去点 DOM。

## 六、已知坑（踩过的，别再踩）

- 本会话环境带 `ELECTRON_RUN_AS_NODE=1`：直接跑 Electron 会当 Node 执行、静默退出；抓图要 `env -u ELECTRON_RUN_AS_NODE` 且加 `--no-sandbox --disable-gpu`。
- Electron 启动脚本暂存 bundle 时必须带上 `knowledge/`（语料不在 `data/` 下），否则窗口里知识库显示 0 篇，而单测全绿。
- 不要占用 3210 端口起后端（Electron 主窗口自己拥有它）；抓图装置用 3341。
- 改动渲染层后需要刷新页面；改了后端要重启服务（AGENTS.md 要求真机验证）。

## 七、下一阶段（用户 2026-10-13 提出）：联网版 / 多端

用户要的是**这四个**（服务端与安卓先不做，iOS + 网页 + 电脑端先做），并且：
账号密码登录、从服务器同步账号数据（**对话历史 / 记忆库 / 笔记库**）、
以及**局域网直传**：两个设备在同一局域网时通过 **8886 端口**传输数据实现自动同步。

好消息：**不用重写**。现在的结构天然适合多端 ——
- 后端已经是 HTTP + WebSocket 服务（`src/server/index.js`，零运行时依赖）；
- 前端是**零构建静态资源**（`src/renderer/**`，纯 HTML/CSS/JS，靠 `PC.api()` 走 HTTP）；
- 电脑端就是现有的 Electron 壳。

所以各端的实现路径是：
| 端 | 做法 | 工作量 |
| --- | --- | --- |
| 网页版 | 同一份 `renderer/` 由服务端托管 + 多用户隔离 + 账号登录 | 小（已有 90%） |
| 电脑端 | 现有 Electron（连本地或远端服务） | 已有 |
| iOS | 先 PWA（今天可用、可离线、加到主屏），再用 Capacitor 包壳上架 | 中 |
| 安卓 | 同 iOS 的壳（用户说先不管） | 中 |
| 服务端 | 账号 / 会话令牌 / 按用户隔离的数据存储 + 增量同步 API | 大（新写） |
| 局域网直传 | 每端一个 8886 同步服务：UDP 广播发现同伴 + HTTP 传输 + 冲突合并 | 中 |

### 必须由用户拍板的问题（已向他提出，等答复）
1. 服务器部署在哪（自建云主机 / 校内机器 / 先本地）—— 决定 TLS 与 iOS 能否直连 http。
2. 账号体系：自建邮箱+密码，还是复用已验证的学校统一身份（CAS）？是否多设备同时在线。
3. 冲突策略：服务器优先 / 时间戳晚者胜 / **两份都留让用户选**（推荐，数据不丢）。
4. 是否要端到端加密（服务端也读不到对话与记忆）—— 代价：密码丢失即数据不可恢复、服务端无法检索。
5. iOS 交付形式：PWA / Capacitor 包壳上架 / 原生 Swift。
6. 局域网 8886：设备间**直传**（无服务器）还是以服务器为中转；TCP+HTTP 传输、UDP 广播发现是否可以。
7. 是否离线优先（无网可用、联网自动补同步）—— 建议必须要。

### 与当前工作的关系（重要）
同步层要建在**稳定的数据模型**上：对话 / 记忆 / 笔记 / 日程 / 成绩的字段一旦还在变，
同步就会变成流沙上的工程。所以顺序是：**先把单机版这四件事做完并验证 → 再抽同步层**。
