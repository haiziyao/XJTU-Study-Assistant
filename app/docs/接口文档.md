# 接口文档 · AI 智学程序后端

> 面向 AI 智学主程序的**模块级接口契约**。后端是「框架（`src/core`）+ 可插拔功能模块（`src/modules`）」
> 的结构，本文覆盖通用约定、日历与待办模块、思源学堂模块、**记忆（Agent 记忆）契约**，以及 AI 接入契约。
> AI 部分本阶段**只留接口**，不接入任何模型；记忆（第 10 节）同样只有契约，代码未落地。
>
> - 新增功能请读 [模块开发指南.md](模块开发指南.md)
> - 运行时可通过 `GET /api/v1/modules` 探测当前装配了哪些模块

- 服务地址：`http://127.0.0.1:3210/api/v1`（默认端口 3210，被占用时自动 +1 递增，实际地址由主进程通过 IPC 告知）
- 推送地址：`ws://127.0.0.1:3210/ws`
- 数据存储：`app/data/*.json`（原子写，单机单用户，无账号体系）；集合清单由各模块在 `module.js` 里声明
- 时间表示：日期一律 `YYYY-MM-DD`；时刻一律 `HH:mm`（24 小时制，本地时区）；时间戳为带偏移的 ISO 8601（如 `2025-10-20T15:00:00+08:00`）
- **宽松输入**：日期接受 `2026-9-1`、`2026/09/01`、`2026年9月1日`、`20260901`，时刻接受 `9:00`，由服务端归一化后存储（与 dschat 2 的 `_parse_date_loose` 行为一致）

## 1. 通用约定

### 1.1 响应包装

成功：

```json
{ "ok": true, "item": { "id": "…", "title": "项目周会" } }
```

失败：

```json
{
  "ok": false,
  "error": {
    "code": "BAD_REQUEST",
    "message": "字段 date 不合法：必须是 YYYY-MM-DD 格式的合法日期",
    "details": { "field": "date" }
  }
}
```

### 1.2 错误码

| code | HTTP | 含义 |
| --- | --- | --- |
| `BAD_REQUEST` | 400 | 参数校验失败，`details.field` 指出字段 |
| `NOT_FOUND` | 404 | 记录不存在，或指令未匹配到对象 |
| `CONFLICT` | 409 | 预留（当前时间冲突只提示不阻断） |
| `PARSE_FAILED` | 422 | 指令无法解析 |
| `AI_UNAVAILABLE` | 501 | AI 能力未接入（本阶段默认） |
| `NOT_IMPLEMENTED` | 501 | 能力已定契约、未实现（当前无此类接口：农历已实现） |
| `INTERNAL` | 500 | 服务内部错误 |

### 1.3 数据落盘格式

每个集合一个文件，写入使用「临时文件 + rename」原子替换；单个文件解析失败时**先备份为 `*.corrupt-<时间戳>`** 再以空集合启动，绝不静默覆盖。

```json
{ "schemaVersion": 1, "items": [ { "id": "…", "createdAt": "…", "updatedAt": "…" } ] }
```

| 文件 | 集合 | 内容 |
| --- | --- | --- |
| `data/events.json` | 日历事件 | 日期/日期区间粒度 |
| `data/schedules.json` | 日程 | 时段粒度 + 提醒（**日程没有完成态**） |
| `data/todos.json` | 待办 | 截止日 + 预估工时 + 优先级 + **完成态** |
| `data/command-logs.json` | 指令日志 | 供前端「最近指令」与后续 AI 复盘 |
| `data/ai-conversations.json` | AI 会话 | 对话会话（标题 / 消息数 / 最后消息时间） |
| `data/ai-messages.json` | AI 消息 | 一问一答 + 抽出来的指令草稿（见 6.4） |

> 模块私有文件不走 JsonStore：思源学堂的登录态 `data/lms-session.json`、AI 的密钥与参数 `data/ai-config.json`，
> 都是 `0600` 的单独文件（凭据不该混在业务数据里，也便于一键清除）。

## ★ AI 速查：加「待办」/「日程」/「日历事件」（先读这节）

> 目标：**模型照着这节就能把三件事准确写进库**，不必理解重复规则、冲突检测、顺延这些细节。
> 机器可读的工具清单在 `GET /api/v1/ai/capabilities` 的 `aiTools` 字段里
> （每项含 `name / description / method / path / params / mutates`，`module: "calendar"` 的就是本模块）。
>
> 「这句到底该记成待办，还是该存进记忆？」——先看**第 10 节的判定表**。
> 一句话：**有确切时间位置 → 本节的三个集合；跨会话的偏好与事实 → 记忆（第 10 节，本阶段仅契约）。**

### 判定表：先选集合，再调接口

| 用户想要 | 落到哪个集合 | 接口 | 最小 body |
| --- | --- | --- | --- |
| **待办**：某天要做完的一件事，没有具体时刻（交作业、交实验报告、报名） | `Todo` | `POST /todos` | `{ "title": "交实验报告", "deadline": "2026-10-12" }` |
| **日程**：有明确起止时刻（明天 15 点开会、周一 9 点半英语晨读） | `Schedule` | `POST /schedules` | `{ "title": "项目周会", "date": "2026-10-12", "startTime": "15:00", "endTime": "16:00" }` |
| **跨天的日期区间**：考试周、假期、持续多天的事 | `Event` | `POST /events` | `{ "title": "期中考试", "startDate": "2026-10-20", "endDate": "2026-10-22", "category": "exam" }` |
| **单日的事件标记**：纪念日、报名截止日 | `Event` | `POST /events` | `{ "title": "报名截止", "startDate": "2026-10-12", "category": "deadline" }` |

### 三条铁律

1. **待办是独立集合 `Todo`，只走 `/todos`。** 待办列表只读 `/todos`（未完成用 `?completed=false`）；
   用 `POST /schedules` 或 `POST /events` 建的「待办」都不会出现在待办列表里。
2. **日程必须有 `startTime`。** `POST /schedules` 缺 `startTime` 会返回 400；传 `allDay` 或 `status`
   同样 400（日程没有「全天」形态，也没有完成态）。**不要用 `/schedules` 建待办。**
3. **「完成」只属于待办。** 只有 `POST /todos/{id}/completed` 能改完成态；
   日程与日历事件都没有完成态，对它们执行「完成」会返回 400。
   反过来：不要把「开会」「上课」这类时段安排放进待办列表，也不要去「完成」它们。

### 最容易写错的两处（都实测过）

| ❌ 错误写法 | 后果 | ✅ 正确写法 |
| --- | --- | --- |
| `POST /schedules { "title": "交实验报告", "date": "2026-10-12" }` | **400**：字段 `startTime` 必填（日程必须是时段） | `POST /todos { "title": "交实验报告", "deadline": "2026-10-12" }` |
| `POST /schedules { "title": "交实验报告", "date": "2026-10-12", "allDay": true }` | **400**：日程没有全天形态；只有日期的请用待办 | `POST /todos { "title": "交实验报告", "deadline": "2026-10-12" }` |

第一条的报错原文（`details.field` 直接指出字段名）：

```json
{ "ok": false, "error": { "code": "BAD_REQUEST", "message": "字段 startTime 必填：日程必须是时段；只有日期的条目请用待办 POST /todos", "details": { "field": "startTime" } } }
```

### 可直接复制的请求

**加待办**（`deadline` 必填，可再带 `estimatedHours / priority / description / tags`）：

```bash
curl -sS -X POST http://127.0.0.1:3210/api/v1/todos \
  -H 'Content-Type: application/json' \
  -d '{"title":"交实验报告","deadline":"2026-10-12","estimatedHours":2,"priority":2,"tags":["物理"],"source":"ai"}'
```

```json
{
  "ok": true,
  "item": {
    "id": "…", "title": "交实验报告", "deadline": "2026-10-12", "estimatedHours": 2,
    "priority": 2, "completed": false, "completedAt": null, "tags": ["物理"], "source": "ai",
    "isOverdue": false, "isToday": false, "daysRemaining": 1,
    "complexity": "normal", "complexityLabel": "一般"
  }
}
```

**加日程**（`startTime` 必填；`endTime` 可选，不传就没有结束时刻）：

```bash
curl -sS -X POST http://127.0.0.1:3210/api/v1/schedules \
  -H 'Content-Type: application/json' \
  -d '{"title":"项目周会","date":"2026-10-12","startTime":"15:00","endTime":"16:00","category":"meeting","source":"ai"}'
```

响应会额外带 `conflicts`（同时间段的重叠提示，**只提示不阻断**，不影响创建成功）。

### 写完之后的常用动作

| 想做什么 | 怎么做 |
| --- | --- |
| 完成一条**待办** | `POST /todos/{id}/completed`，body `{ "completed": true }`（取消完成传 `false`） |
| 顺延未完成的待办 | `POST /todos/rollover`，body `{ "weekStart": "2026-10-12" }`（周一；缺省本周一） |
| 改一条 | `PATCH /todos/{id}` / `PATCH /schedules/{id}` / `PATCH /events/{id}`（局部更新） |
| 删一条 | `DELETE /todos/{id}` / `DELETE /schedules/{id}` / `DELETE /events/{id}` |
| 查回来核对 | `GET /todos?completed=false`（未完成待办）、`GET /todos/upcoming`（最近要交的）、`GET /schedules?date=2026-10-12`（当天时段日程）、`GET /events?from=…&to=…` |
| 一天的全貌 | `GET /calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`（事件 + 时段日程 + 当天截止的待办） |
| 这周排了多少课 | `GET /schedules/stats?from=…&to=…`（只统计时段日程：条数 + 计划时长） |

**分类可选值**：`category` **就是分类 id**，合法取值来自 `GET /categories?kind=schedule|event` 的 `id`。
**留空或传无效值不会报错，会静默落到 `other`** —— 所以「先建分类再写日程」不是必需的，
但想让日程显示成自定义颜色就必须先建分类。

**四个必须记住的约定**

1. **「完成」只对待办有意义**：`POST /todos/{id}/completed` 是唯一入口。
   对日程或日历事件执行「完成」会返回 400（`日程没有完成态，完成只属于待办：…`）。
2. **`source` 默认是 `manual`**：直接 `POST` 建出来的记录不会自动标成 AI。模型写库请显式传 `"source": "ai"`，
   这样事后能分清哪些数据是模型加的（枚举 `manual / command / ai / import`）。
3. **`POST` 不幂等**：同一句话调两次会建两条记录。要防重，先查一下
   （`GET /todos?keyword=…` 或 `GET /schedules?date=…&keyword=…`）再决定新建还是 `PATCH`；
   需要强幂等的导入通道请用 `externalId`（如思源学堂同步，见第 9 节）。
4. **日期/时刻格式**：日期 `YYYY-MM-DD`，时刻 `HH:mm`（24 小时制）。宽松写法（`2026-10-12`、`2026/10/12`、`9:00`）服务端会归一化，
   但**整数时间戳、带时区的 ISO 串不被接受**。跨零点请拆成两条日程。

### 只想给一句中文？

两条路都能落地（后者更适合需要用户确认的场景）：

- `POST /commands/run { "text": "添加待办 明天 交实验报告" }` —— 服务端用本地规则解析并**直接落库**；
- `POST /commands/parse { "text": "…" }` → 把返回的 `draft` 交给用户确认 → `POST /commands/execute { "draft": … }`。

指令对象契约见 4.2；`target`（`todo` / `schedule` / `event`）的判定规则见 4.3 —— 与本节的三条铁律一致。

## 2. 数据模型

### 2.1 日历事件 Event（日期粒度）

用于**跨天或日期粒度**的事项：假期、考试周、纪念日，以及「报名截止」这类只标一天的日子。

> ⚠️ **单日的待办不要写到这里。** 「明天交实验报告」这类没有时刻的单日事项请用
> `POST /todos`（它就是待办）—— 待办列表只读 `/todos`，写成 Event 在待办列表里是看不到的。
> 判定规则见开头「★ AI 速查」。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string(uuid) | 系统生成 | 主键 |
| `title` | string(≤120) | ✅ | 名称 |
| `description` | string(≤2000) | — | 备注，默认 `""` |
| `category` | enum | — | `study / exam / holiday / anniversary / deadline / other`，默认 `other` |
| `startDate` | `YYYY-MM-DD` | ✅ | 开始日 |
| `endDate` | `YYYY-MM-DD` | — | 结束日（含当天），缺省等于 `startDate`；不能早于 `startDate` |
| `allDay` | boolean | — | 默认 `true`（日历事件恒为全天，字段保留以便未来支持跨天定时） |
| `repeat` | Repeat | — | 缺省 `{ "type": "none" }` |
| `color` | string | — | 覆盖默认配色 |
| `tags` | string[] | — | 标签 |
| `source` | enum | — | `manual / command / ai / import`，默认 `manual` |
| `externalId` | string | — | 外部系统 id（如导入的学习记录），用于去重 |
| `createdAt` / `updatedAt` | ISO 8601 | 系统生成 | 审计字段 |

```json
{
  "id": "6f1c…",
  "title": "期中考试",
  "category": "exam",
  "startDate": "2025-10-20",
  "endDate": "2025-10-22",
  "allDay": true,
  "repeat": { "type": "none", "interval": 1, "weekdays": [], "until": { "mode": "never" } },
  "tags": [],
  "source": "command"
}
```

### 2.2 日程 Schedule（时段粒度）

用于上课、自习、会议、约见等**有明确起止时刻**的安排。**`startTime` 必填**，
`endTime` 可选（跨零点请拆成两条）。

> 日程**没有完成态**，也没有「全天」形态：
> - `POST /schedules` 缺 `startTime` → 400（`details.field = "startTime"`）；
> - 传 `allDay` 或 `status` → 400（只有日期的请用 `POST /todos`）。
>
> **历史数据兜底**：早期版本把「待办」写成 `allDay: true` 的日期锚点行。启动时会一次性
> 把它们迁成待办（见第 11 节「已知限制」）；万一迁移失败，`GET /schedules` 也会**永远跳过**这类行，
> `/calendar` 则把它们放进 `imported` 桶只读展示 —— 既不冒充日程，也不会「数据还在但界面看不见」。
> 现在外部导入（思源学堂、dschat 兼容）分别写 `/todos` 与 `/events`，不再产生这种行。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string(uuid) | 系统生成 | 主键 |
| `title` | string(≤120) | ✅ | 名称 |
| `description` | string(≤2000) | — | 备注 |
| `category` | enum | — | `class / study / meeting / exam / activity / other`，默认 `other` |
| `date` | `YYYY-MM-DD` | ✅ | 归属日期（重复日程为首发日） |
| `startTime` | `HH:mm` | ✅ | 开始时刻 |
| `endTime` | `HH:mm` | — | 结束时刻，须 ≥ `startTime`（跨零点请拆两条） |
| `priority` | 0\|1\|2 | — | 0 普通 / 1 重要 / 2 紧急（沿用 PotatoCalendar 三档），默认 1 |
| `estimatedMinutes` | integer | — | 预估时长，用于复杂度与负载统计 |
| `location` | string(≤120) | — | 地点 |
| `tags` | string[] | — | 标签 |
| `reminders` | Reminder[] | — | 最多 5 条 |
| `repeat` | Repeat | — | 缺省不重复 |
| `eventId` | string \| null | — | 关联的日历事件（可空） |
| `source` | enum | — | `manual / command / ai / import` |
| `externalId` | string \| null | — | 来自外部系统时的唯一键（如思源学堂 `lms:activity:5001`），用于重复同步时幂等更新，见第 9 节 |
| `createdAt` / `updatedAt` | ISO 8601 | 系统生成 | 审计字段 |

响应中还会附带**派生字段**（不落库）：`complexity`（由 `estimatedMinutes` 推导：≤60 分钟 `simple`、≤180 `normal`、≤600 `complex`、其余 `heavy`）。

```json
{
  "id": "a83b…",
  "title": "项目周会",
  "category": "meeting",
  "date": "2025-10-21",
  "startTime": "15:00",
  "endTime": "16:00",
  "priority": 1,
  "estimatedMinutes": 60,
  "reminders": [{ "offsetMinutes": 10, "channel": "app", "sent": {} }],
  "repeat": { "type": "weekly", "interval": 1, "weekdays": [2], "until": { "mode": "never" } },
  "source": "command"
}
```

### 2.3 待办 Todo（截止日粒度，**有完成态**）

用于「某天要做完的一件事」：交作业、交实验报告、报名、复习计划。**待办是独立实体**，
不是日程的变体：它只有截止日，没有起止时刻，也没有地点与分类。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string(uuid) | 系统生成 | 主键 |
| `title` | string(≤120) | ✅ | 事项名称 |
| `deadline` | `YYYY-MM-DD` | ✅ | 截止日（不是时段） |
| `estimatedHours` | number | — | 预估工时，默认 `1`；决定复杂度 |
| `priority` | 0\|1\|2 | — | 0 低 / 1 普通 / 2 紧急，默认 `0` |
| `completed` | boolean | — | 完成态，默认 `false` |
| `completedAt` | ISO 8601 \| null | 系统写入 | 勾选时写时间戳，取消勾选时清成 `null` |
| `description` | string(≤2000) | — | 备注 |
| `tags` | string[] | — | 标签 |
| `source` | enum | — | `manual / command / ai / import`，默认 `manual` |
| `externalId` | string \| null | — | 外部系统 id（保留字段） |
| `rolledFrom` | `{ deadline }` | 系统写入 | 被顺延过时记录「这次顺延前原本哪天到期」 |
| `createdAt` / `updatedAt` | ISO 8601 | 系统生成 | 审计字段 |

**响应里的派生字段**（不落库，随「今天」变化，所以绝不存盘）：

| 字段 | 含义 |
| --- | --- |
| `isOverdue` | `未完成 && deadline < 今天` |
| `isToday` | `deadline === 今天` |
| `daysRemaining` | 距离截止日的天数（负数 = 已过期） |
| `complexity` | 由 `estimatedHours` 推导：≤1h `simple`、≤3h `normal`、≤10h `complex`、>10h `heavy` |
| `complexityLabel` | 上面四项的中文：`简单 / 一般 / 复杂 / 繁琐` |

```json
{
  "id": "b7d1…",
  "title": "交实验报告",
  "deadline": "2025-10-24",
  "estimatedHours": 2.5,
  "priority": 2,
  "completed": false,
  "completedAt": null,
  "description": "第三章实验数据",
  "tags": ["物理"],
  "source": "command",
  "isOverdue": false,
  "isToday": false,
  "daysRemaining": 3,
  "complexity": "normal",
  "complexityLabel": "一般"
}
```

**顺延语义**：`POST /todos/rollover` 把「未完成且截止日早于目标周一」的待办，**同一条记录的截止日**
平移到目标周的**同一星期几**（若那天已经过去，则落到目标周一），并写 `rolledFrom.deadline` 保留来源。
不克隆记录、也不改 `completed`。

### 2.4 重复规则 Repeat

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | enum | `none / daily / weekly / monthly / yearly / weekday` |
| `interval` | integer ≥1 | 间隔，例如「每两周」= `interval: 2` |
| `weekdays` | integer[] | ISO 星期（1=周一 … 7=周日），`weekly` 使用；`weekday` 固定周一至周五 |
| `until.mode` | enum | `never`（默认）/ `date` / `count` |
| `until.date` | `YYYY-MM-DD` | `mode = date` 时必填 |
| `until.count` | integer | `mode = count` 时必填（总次数） |

**展开语义**（与 PotatoCalendar 的隐式取模不同，这里是结构化规则）：

- `daily`：锚点日起每 `interval` 天；
- `weekly`：锚点日所在周的 `weekdays` 命中，且周序号间隔为 `interval`；
- `monthly`：与锚点同日；锚点是当月最后一天时，匹配每月最后一天（修正了「31 号在 2 月消失」的问题）；
- `yearly`：与锚点同月同日（含月末修正）；
- `weekday`：周一至周五；
- 重复实例是**查询时惰性展开**，不落库，因此修改规则即时生效。

### 2.5 提醒 Reminder

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `offsetMinutes` | integer ≥0 | 提前分钟数，0 表示准点 |
| `channel` | enum | `app / system / ai`，默认 `app` |
| `sent` | object | 系统写入：`{ "2025-10-21": "2025-10-21T14:50:00+08:00" }`，按发生日去重 |

提醒基准：日程取 `date + startTime`；导入的日期锚点（无 `startTime`）取当天 `08:00`。已过窗口（>12 小时）的提醒不补发。

### 2.6 农历 Lunar（框架级能力）

`GET /meta/lunar` 与具体业务无关，属于框架的日期换算能力（实现 `src/shared/lunar.js`，零依赖查表，覆盖 1900-01-31 ~ 2100-12-31）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/meta/lunar?date=YYYY-MM-DD` | 单日：`{ date, lunar:{ year, zodiac, month, day, isLeapMonth, monthNumber, dayNumber }, festivals:[], text }` |
| GET | `/meta/lunar?from=&to=` | 批量：`{ from, to, days: { 'YYYY-MM-DD': { lunar, festivals, text } } }`，跨度上限 800 天 |

- `month` **不带**「闰」字，闰月由 `isLeapMonth` 表达；`text` 是给眼睛看的一行（`丙午年九月初三`，闰月写成 `丙午年闰二月初一`）。
- **只做农历节日，不做节气**：节气需要天文算法，近似值就是错数据。节日 = 春节 / 元宵 / 端午 / 七夕 / 中元 / 中秋 / 重阳 / 腊八 / 除夕（除夕按「次日是正月初一」判定）。
- 前端：日视图顶部显示 `text`（有节日时追加 `· 节日名`，accent 色）；月视图每格一行农历小字（节日优先 → 初一显示月名 → 其余显示日名）；年视图只用日数字 + 有内容的小圆点。

### 2.7 分类 Category（可编辑的分类注册表）

日程与日历事件**各有一套**分类，存在两个集合里：

| 集合 | 文件 | kind |
| --- | --- | --- |
| `scheduleCategories` | `data/schedule-categories.json` | `schedule`（日程分类） |
| `eventCategories` | `data/event-categories.json` | `event`（日历事件分类） |

**一句话：`category` 就是分类 id**。可选值来自 `GET /categories?kind=schedule|event` 的 `id`；
**留空或无效会落到 `other`**（静默兜底，不报错）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 分类 id，**也就是写进日程/事件的 `category` 值**。内置项是裸 id（`class`/`study`/…），自建项是 uuid |
| `kind` | enum | `schedule` / `event`，由所在集合推出（响应里带上，方便前端） |
| `label` | string(≤12) | 显示名（用户可改；改名字**不影响 `id`**，所以历史数据不会失联） |
| `color` | `#RRGGBB` | 颜色（用户可改），前端用它渲染日历里的色条/色块 |
| `order` | number | 排序，小者在前；`other` 的 order 最大，天然在最后 |
| `builtin` | boolean | 是否内置（内置项可以改名/改色，也参与排序） |
| `locked` | boolean | `true` 表示**不可删除**（只有内置的 `other`） |
| `inUse` | number | 只读：该分类下的记录条数（日程看 `schedules`、事件看 `events`） |

**为什么拆两个集合**：两个 kind 本来就各管各的，而它们**共用** `study` / `exam` / `other`
这些名字。合在一张表里（集合以 `id` 为唯一键）记录 id 就不再等于「写进日程的那个值」，
得引入 key/value 两层间接；拆开之后 `id` 即值，读写都不用转换。

**写库时的分类校验语义**：`category` 传**该 kind 里存在的 id** 就用它；**没传或不存在 →
静默落到 `other`**（分类写错不该让用户的日程写不进去；dschat 兼容层的自由文本也靠这条容错）。

首次启动会播种内置分类（**每个集合各自为空时**才播种，用户改过就不覆盖）：

| kind | 内置 id（按 order） |
| --- | --- |
| `schedule` | `class`（上课 #6c8cff）/ `study`（学习 #5cdb8b）/ `meeting`（会议 #c792ea）/ `exam`（考试 #ff6b7a）/ `activity`（活动 #ffb86c）/ `other`（其它 #83838f，locked） |
| `event` | `study`（学习 #5cdb8b）/ `exam`（考试 #ff6b7a）/ `holiday`（假期 #ffb86c）/ `anniversary`（纪念日 #c792ea）/ `deadline`（截止 #ff6b7a）/ `other`（其它 #83838f，locked） |

curl -s localhost:3210/api/v1/compat/dschat/events -H 'Content-Type: application/json' \
  -d '{"title":"每周例会","date":"2026-09-20","start_time":"10:00","end_time":"11:00","repeat":"weekly","repeat_interval":2,"repeat_end":"2026-12-31"}'
```

字段映射规则：

| dschat 2 | 本模块 | 说明 |
| --- | --- | --- |
| `title` | `title` | 必填 |
| `date` | `date`（→ `Schedule`）/ `deadline`（→ `Todo`） | dschat 2 只有单日锚点：**有时刻**转时段日程，**没有时刻**转待办（截止日 = 该日期） |
| `start_time` / `end_time` | `startTime` / `endTime`（→ `Schedule`） | 宽松归一化（`9:00` → `09:00`）；两者都没有 → 待办，没有时刻可写 |
| `all_day` | 决定落点 | `1/0` 亦接受；`all_day: 1`（或没有时刻）→ `Todo`，否则 → `Schedule` |
| `notes` | `description` | 别名 |
| `location` | `location` | 同名 |
| `repeat` + `repeat_interval` + `repeat_end` | `repeat: { type, interval, until }` | `每2周` 这类写法也能解析；`无` → `none` |
| `priority`（todo，high/medium/low） | `priority`（2/1/0） | 待办标记行会做映射 |
| `category` / `科目` | `category`（固定枚举）+ `tags` | dschat 2 是自由文本，本项目用枚举，原文保留在 `tags` |
| `completed`（todo 布尔） | 待办的 `completed`（写 `true` 即完成并记 `completedAt`） | 显式布尔优先，旧形状的 `status: done/pending` 作为兜底也会被折回布尔（详见 7.2）；新代码请走 `/todos` |
| `user_id` | 无 | 本模块单机单用户，多租户隔离由主程序负责 |
| — | `startDate` / `endDate` | 跨天区间为本模块新增能力，dschat 2 无对应字段 |

## 4. 指令添加

### 4.1 三种调用方式

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/commands/parse` | 只解析，返回「指令对象」，供前端确认卡片 |
| POST | `/commands/execute` | 执行一个既有「指令对象」（body 传 `draft`）或现解析现执行（body 传 `text`） |
| POST | `/commands/run` | 解析 + 执行一步到位 |

三个接口都支持 `dryRun: true`：只返回将执行的动作，不写库。

`POST /commands/parse` 请求 / 响应：

```

```json
{
  "ok": true,
  "draft": {
    "ok": true,
    "raw": "添加日程 明天 15:00-16:00 项目周会 提前10分钟提醒",
    "action": "create",
    "target": "schedule",
    "fields": {
      "source": "command",
      "date": "2025-10-16",
      "startTime": "15:00",
      "endTime": "16:00",

### 4.2 指令对象（统一契约）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ok` | boolean | 是否解析成功 |
| `raw` | string | 原始输入 |
| `action` | enum | `create / query / update / delete / complete / rollover` |
| `target` | enum | `event`（日历事件）/ `schedule`（日程） |
| `fields` | object | 写操作字段，与第 2 章模型同名字段一致 |
| `filters` | object | 查询/删除条件：`{ from, to, status, keyword }`；`rangeLabel` 仅用于展示 |
| `confidence` | number | 0~1 置信度 |
| `warnings` | string[] | 需要用户确认的疑点（如"未识别到日期，默认今天"） |
| `explain` | string | 给用户看的一句话说明 |
| `provider` | string | 仅 AI 来源时出现：`rules` 表示本地规则降级 |

> 前端推荐流程：`parse` → 展示 `explain` 与低置信度 `warnings` → 用户确认 → `execute`。
> AI 接入后只需让模型产出同样的 `draft`，落库逻辑完全复用。

### 4.3 指令语法速查

`GET /commands/grammar` 返回机器可读版本，摘要如下：

```
[动作] [对象] [时间] [名称] [重复] [提醒] [优先级]
```

| 维度 | 支持写法 |
| --- | --- |
| 动作 | 创建：`添加 / 新建 / 创建 / 安排 / 记一下 / 提醒我`；查询：`查询 / 查看 / 列出 / 显示 / 有哪些`；修改：`修改 / 改成 / 改到 / 推迟 / 挪到`；删除：`删除 / 删掉 / 移除 / 取消`；完成：`完成 / 做完 / 打卡 / 勾选`（**只对待办**）；顺延：`顺延 / 挪到下周`（**只对待办**） |
| 对象 | 日历事件：`日历事件 / 日历 / 纪念日 / 假期 / 生日`；日程：`日程 / 安排 / 课程 / 上课 / 自习 / 会议 / 例会 / 周会 / 站会 / 面试`；待办：`待办 / 任务 / 作业 / 截止 / 提交 / 报名 / 打卡 / 完成`。**判定顺序（三路）**：① 明确措辞优先（事件 → 日程）；② 待办措辞 → `todo`；③ 跨天日期区间 → `event`；④ 有具体时刻 → `schedule`；⑤ 其余单日无时刻 → `todo` |
| 日期 | `今天 / 明天 / 后天 / 大后天 / 下周三 / 周五 / 周末 / 10月20日 / 2025-10-20 / 10月20日到10月22日` |
| 时刻 | `15:00`、`15:00-16:00`、`下午3点`、`下午3点半`、`晚上7点到8点`、`全天`、`15:00 起 1 小时` |
| 重复 | `每天`、`每周一`、`每两周`、`每月1日`、`每年`、`工作日` |
| 提醒 | `提前10分钟`、`提前半小时`、`提前1天`、`提醒` |
| 优先级 | `重要 / 紧急` → 2；`不急` → 0；**待办默认 0（低），日程/事件默认 1（普通）** |
| 工时 | `预计2小时`、`半小时`、`30分钟` → 待办的 `estimatedHours`（缺省 1） |
| 标签 | `#实验` → 待办的 `tags` |
| 分类 | 关键词自动判定，如「上课→class」「刷题/背单词→study」「考试→exam」「开会→meeting」 |

**示例与解析结果**

| 指令 | 解析要点 |
| --- | --- |
| `添加日程 明天 15:00-16:00 项目周会 提前10分钟提醒` | create/schedule，`date=明天`，15:00-16:00，提醒提前 10 分钟 |
| `明天 交实验报告` | create/**todo**，`deadline=明天` —— 单日且无时刻，算待办（不是 schedule，也不是 event） |
| `添加待办 明天 交实验报告 预计2小时 重要 #实验` | create/todo，「待办」是明确措辞；`estimatedHours=2`、`priority=2`、`tags=["实验"]` |
| `添加日程 每周一 9点半 英语晨读` | `repeat={type:weekly,weekdays:[1]}`；锚点在过去时自动滚动到下一个周一 |
| `添加日历事件 2025-10-20 到 2025-10-22 期中考试 重要` | create/event，`startDate~endDate`，`category=exam`，`priority=2` |
| `2026-01-20 到 2026-02-20 寒假` | create/event，**跨天区间**即使不写「日历事件」也判事件 |
| `添加日程 明天 开会` | **明确说了「日程」但没有时刻** → 按 `09:00-10:00` 排入时间轴，并给出警告（不会退化成待办） |
| `查询本周未完成的待办` | query/todo，`filters={from:本周一,to:本周日,completed:false}` |
| `把明天的项目周会改到 16:00` | update/schedule，`filters={from:明天,to:明天,keyword:项目周会}`，`fields.startTime=16:00` |
| `完成今天的英语听力` | complete/**todo**，`filters.completed=false` —— 「完成」只属于待办，只会命中待办 |
| `完成明天的项目周会` | 「周会」是日程措辞 → complete/**schedule** → **400**「日程没有完成态，完成只属于待办」 |
| `顺延未完成的待办到本周` | rollover/todo，`filters.weekStart=本周一` |
| `删除日程 项目周会` | delete/schedule |

### 4.4 指令日志

`GET /commands/logs?limit=50` 返回最近的指令记录（倒序）：`text / action / target / confidence / ok / affectedCount / source`，供前端展示「最近指令」，也为后续 AI 复盘与评测提供样本。

## 5. WebSocket 协议

连接 `ws://127.0.0.1:<port>/ws`，服务端推送 JSON 文本帧：

| type | payload | 说明 |
| --- | --- | --- |
| `ready` | `{ clients }` | 握手完成 |
| `reminder` | `{ scheduleId, title, date, startTime, offsetMinutes, channel, triggerAt, occurrenceDate }` | 到点提醒；主进程同时弹系统通知 |
| `data_changed` | `{ target, action, id? , count? }` | 数据变更，前端据此刷新 |
| `error` | `{ message }` | 预留 |
| `ai_delta` | `{ conversationId, messageId, delta, text }` | **模块推送**（`module: "ai"`）：流式对话的一个增量 |
| `ai_message` | `{ conversationId, message, drafts }` | **模块推送**（`module: "ai"`）：一条 AI 消息最终定稿（成功或失败） |

客户端可发送 `{"type":"ping"}`，服务端回 `{"type":"pong"}`。

> 上面的 `ready` / `reminder` / `data_changed` 是**框架**的消息；模块也可以推送自己的 `type`
> （带上 `module` 字段即可），前端按需分支。AI 流式对话就是这么做的（见 6.4），
> 这样 HTTP 端不需要处理半截的流式响应，断线重连后一次请求就能拿到完整结果。

  当前 `aiTools` 共 **29** 个 = 日历 **19**（`modules/calendar/tools.js`：事件 3 读 3 写、日程 2 读 3 写、

### 6.2 主程序如何接入

在后端进程内注册 provider 即可，无需改路由：

```js
import { createServer } from './app/src/server/index.js';

const app = await createServer();
app.aiBridge.registerProvider({
  name: 'dschat2',
  // text: 用户输入；context: { now, view, recent } 由调用方透传
  async nlToCommand(text, context) {
    // 调用大模型，产出与 4.2 完全一致的指令对象
    return { ok: true, action: 'create', target: 'schedule', fields: {…}, confidence: 0.9, warnings: [], explain: '…' };
  },
});
```

契约要点：

1. provider **只负责理解**，返回 draft，不直接写库；落库仍走本地校验与业务服务，避免模型产出脏数据；
2. 返回结构必须与第 4.2 节一致，字段名与第 2 章模型同名；
3. 无法确定时应降低 `confidence` 并在 `warnings` 中说明，前端据此要求用户确认；
4. `AI_CONTRACT_VERSION`（当前 `1.0.0`）用于向后兼容判断；
5. 产出的 `fields.source` 请写 `"ai"`（本地规则写 `"command"`），否则事后分不清哪些数据是模型加的；
6. provider 若选择直接落库（不走 draft），请用 `POST /schedules` / `POST /events` 并**显式传 `"source": "ai"`** —— 这两个接口默认写 `manual`。

### 6.4 对话接口（`modules/ai/`，已实现）

模块 `ai`（order 90，排在所有业务模块之后：它要读待办/日程做摘要，也要经 `services.commands` 预校验草稿）。

**配置**（密钥只进不出：接口永远不返回原值，错误信息里的密钥也会被抹成 `***`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/ai/status` | `{ configured, provider, ready, config, conversations, messages }` —— 前端据此显示「AI 未配置」还是模型名 |
| GET | `/ai/config` | 当前配置（`hasKey` + `keyHint` 末四位，**没有 `apiKey`**） |
| POST | `/ai/config` | 改配置：`{ apiKey?, baseUrl?, model?, temperature?, timeoutMs?, historyTurns?, drawMode?, provider? }`；`apiKey: ""` 表示清空 |
| DELETE | `/ai/config` | 清掉磁盘上的配置（回落到环境变量，同时注销 provider） |

优先级：`createServer({ ai: {...} })` > `data/ai-config.json`（0600）> 环境变量 `PC_AI_*` > 内置默认（DeepSeek 的 OpenAI 兼容端点）。
环境变量：`PC_AI_API_KEY / PC_AI_BASE_URL / PC_AI_MODEL / PC_AI_PROVIDER / PC_AI_TIMEOUT_MS / PC_AI_TEMPERATURE / PC_AI_HISTORY_TURNS / PC_AI_DRAW_MODE`。

`drawMode`（默认 `true`，沿用 dschat2 的 `draw_mode`）控制**是否把绘图说明写进系统提示词**。
关掉只是"别主动画"；用户话里出现「画 / 绘制 / 作图 / 图表 / 函数图 / 示意图 / 坐标」这类**指令词**时，
服务端仍会为那一轮临时开启（`modules/ai/chat-service.js` 的 `DRAW_KEYWORDS`）。

**对话**：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/ai/chat` | `{ text, conversationId?, context?, stream? }` → 存两条消息并返回 `{ conversation, user, assistant, drafts, queried }` |
| GET | `/ai/conversations` | 会话列表（按最后消息时间倒序） |
| POST | `/ai/conversations` | 新建空会话 `{ title? }` |
| GET | `/ai/conversations/:id` | 会话详情 + 全部消息 |
| DELETE | `/ai/conversations/:id` | 删会话并连带删它的消息 |
| DELETE | `/ai/conversations` | **清空全部**会话与消息（设置页那一键），返回 `{ conversations, messages }` 计数 |
| GET | `/ai/context` | **给模型的上下文**：`{ now, today, view, memory, recent }`（形状见 10.7） |

```bash

curl -s -X POST localhost:3210/api/v1/ai/config -H 'Content-Type: application/json' \
  -d '{"apiKey":"sk-…","model":"deepseek-chat"}'

# 2) 聊一句（stream: true 时增量走 WebSocket）
curl -s -X POST localhost:3210/api/v1/ai/chat -H 'Content-Type: application/json' \
  -d '{"text":"明天交实验报告，预计两小时"}'
```

响应（截断）：

```json
{
  "ok": true,
  "conversation": { "id": "…", "title": "明天交实验报告，预计两小时", "messageCount": 2 },
  "user": { "id": "…", "role": "user", "content": "明天交实验报告，预计两小时" },
  "assistant": {
    "id": "…", "role": "assistant", "status": "done",
    "content": "我准备这样加一个待办，你确认一下。",
    "model": "deepseek-chat",
    "usage": { "prompt_tokens": 812, "completion_tokens": 96, "total_tokens": 908 },
    "raw": "…抽掉代码块之前的原文（有草稿时才有）…"
  },
  "queried": [],
  "drafts": [
    {
      "draft": { "ok": true, "action": "create", "target": "todo",
                 "fields": { "title": "交实验报告", "deadline": "2026-10-13", "estimatedMinutes": 120, "priority": 2 } },
      "preview": { "ok": true, "dryRun": true, "planned": { "……模型原样给的字段……" }, "validated": { "……校验归一化后的字段……" } },
      "error": null
    }
  ]
}
```

**模型只能"提议"，不能写库**（这是这套接口最重要的一条）：

1. 提示词要求模型在自然语言之外附一段 ` ```command ` 代码块，里面是**一个** 4.2 形状的指令对象；
2. 服务端把它抽出来（`content` 里给用户看的文本不含代码块，原文留在 `raw`），
   再调 `commands.execute(draft, { dryRun: true })` 跑一遍**真实的字段校验**（不写库、不广播、不记日志）；
3. 校验结果进 `drafts[].preview.validated`；不合法则 `preview: null` + `error.details.field`
   （例：日程缺 `startTime`）—— **聊天本身仍然成功**，用户看到的是"这条草稿有问题"；
4. 用户点确认后，前端照旧 `POST /commands/execute`（与本地规则走同一条路），
   所以 `source`、指令日志、`data_changed` 广播都不会漏。

> `dryRun` 的返回里有两个字段：`planned` 是**模型原样给的**字段，`validated` 是**跑过真实校验/归一化后**的最终值。
> 两者都要给前端 —— 前者用来告诉模型/用户"想干什么"，后者用来保证"真写进去的是这个"。

**唯一的例外：只读查询自动执行。** `action: "query"` 的草稿**不需要用户确认**，
服务端直接执行（同样走 `dryRun`，只读、不记日志），然后把结果**回灌给模型**再要一次回答：

```
用户："我明天有什么日程"
  → 模型第 1 次回复：查询草稿 {action:"query", target:"schedule", filters:{from,to}}
  → 服务端执行查询 → 把结果放进一条带 [系统注入] 标注的消息 → 第 2 次调用模型
  → 模型第 2 次回复：自然语言答案（"你明天只有一件事：10:00–11:00 …"）
  → HTTP 响应：assistant.content = 答案，queried = 原始数据（前端据此画数据行），drafts = []
```

- 为什么必须这样：模型看不见数据就只能说"**我拿不到查询结果 / 需要你确认**"，
  而用户问的是"我明天有什么课" —— 这类问题应该直接给答案；
- 只读是硬前提：写操作（create / update / delete / complete）**仍然**必须走确认卡，一步都不能省；
- 一轮最多自动执行 **3** 个查询，单次最多回灌 **20** 条（只留回答需要的字段，不把整库塞进提示词）；
- 查询条件必须写在 **`filters`**（`from` / `to` / `completed` / `overdue` / `keyword` / `category`）里。
  模型偶尔会误写进 `fields.date`，服务端会兜住并搬到 `filters.from/to` ——
  否则不是"查不到"，而是**没加条件地查了整个库**，答案看着还挺像真的，那更糟；
- 第二次调用失败（超时/上游报错）**不影响已经拿到的数据**：响应里 `queried` 照给，
  消息 `error.code = "PARTIAL"` 说明"数据有了、总结没成"。

**流式**：`stream: true` 时增量通过 WebSocket 推送（`ai_delta` → `ai_message`，见第 5 节），
HTTP 仍然**一次性**返回最终结果 —— 断线重连后重发一次请求就能拿到完整答案，前端不必处理半截的 HTTP 流。

**失败也留痕**：上游报错（401 / 超时 / 网络）翻译成 `502 UPSTREAM_ERROR`，
那条 assistant 消息以 `status: "failed"` + `error` 落库，用户能看到"刚才那次没成"，消息不会静默消失。

#### 回复体的格式约定（模型 ↔ 渲染器）

`assistant.content` 是 **Markdown 子集 + LaTeX 子集**，前端用自己写的渲染器（`kit/richtext.js`，零依赖）
渲染成 HTML。写模型提示词/换 provider 时要按这套来，否则界面上就是一堆原始符号：

| 能力 | 写法 | 说明 |
| --- | --- | --- |
| 强调 | `**粗**` `*斜*` `` `代码` `` `~~删除~~` | 标题 `##`、列表 `-` / `1.`、引用 `>`、分隔线 `---`、围栏代码块 |
| 行内公式 | `$…$` | 也认 `\(…\)` |
| 块级公式 | `$$…$$`（独立成行） | 也认 `\[…\]` |
| 公式子集 | `^ _ \frac{}{} \sqrt{} \sqrt[n]{} \sum_{}^{} \int_a^b \alpha…\Omega \le \ge \ne \to \in \sin \ln \lim \vec{} \text{}` | 不认识的命令**原样显示**（标成橙色）而不是静默丢掉 |
| **不支持** | `\begin{…}` 矩阵/分段函数、`\displaystyle`、自定义宏 | 写进提示词让模型避开；渲染器不假装支持 |
| 图形 | ` ```svg ` 代码块 | 见下 |

**` ```svg ` 图形的硬约束**（CSP 逼出来的，写进提示词也叫了模型）：

- 必须带 `viewBox`；只用 `line / circle / rect / polygon / polyline / path / text / g / defs`；
- **不能用 `style` 属性**：本项目 `style-src 'self'`，内联样式会被浏览器拦掉。
  颜色一律用表现属性（`fill=` / `stroke=` / `stroke-width=` / `font-size=`）；
- 深色背景，别用黑色；提示词里给了可用的配色（`#8f9bb3` / `#e6e6ef` / `#6c8cff` / `#ffb86c`）；
- 服务端/前端会做清理：`script`、`foreignObject`、`iframe`、`object`、`embed`、`on*`、
  `javascript:`、`style=` 一律剥掉；没写 `viewBox` 补一个，根节点没写 `fill` 补 `currentColor`；
- **流式过程中的半截 SVG 不会注入 DOM**（会先显示「正在绘制…」）——
  否则残缺标签会让浏览器把后续内容当成属性值，控制台刷一屏报错。

前端还有一种「操作卡」用于展示查询/写入结果：**默认折叠**，点标题栏展开；
配色按作用对象区分（日程橙、待办紫、日历事件蓝、写入绿）。这是渲染层的事，
但**接口侧的形状决定了它能不能画对**：`queried[].result.target` 与 `drafts[].draft.target` 必须准确
（选错集合不只是"存错地方"，界面上也会给错颜色）。

## 8. 与 dschat 2 的对齐

`dschat 2`（同工作区）是一个 Python 标准库实现的聊天应用，其日历是「**轻量单日事件模型**」：
SQLite `events` 表 + `/api/events` 路由 + 「提示词约定 + 前端正则」的伪工具调用（**没有** OpenAI 风格的 function schema）。

### 8.1 能力对照

| 维度 | dschat 2 | 本模块 | 对齐做法 |
| --- | --- | --- | --- |
| 日期语义 | 单日 `date`，**不支持跨天** | `Event` 支持 `startDate ~ endDate`；`Schedule` 单日 + 时段 | 由本模块承担跨天能力；dschat 2 的单日事件映射为 `Schedule` |
| 时刻 | `start_time` / `end_time`（`HH:MM`） | `startTime` / `endTime` | 字段映射 + 宽松归一化 |
| 全天 | `all_day` 0/1，起止置 NULL | `allDay` 布尔 | 映射；无时刻即视为全天 |
| 重复 | 扁平 `repeat` + `repeat_interval` + `repeat_end`（仅 `none/daily/weekly/monthly/yearly`，无 weekday、无 count） | 嵌套 `repeat{ type, interval, weekdays, until }` | 双向转换；dschat 2 无法表达的「每周一」「共 10 次」在本模块可用 |
| 状态 | event **无状态**；仅 todo 有 `completed` 布尔 | 四态状态机 + `completedAt` | `completed` 布尔 → `status: done/pending` |
| 分类 / 颜色 | event **都没有**（仅 todo 有自由文本 `category`） | 固定枚举 + 自由 `color` | 自由文本「科目」按关键词归入枚举，原文保留到 `tags` |
| 提醒 | 无 | `reminders` + WebSocket + 系统通知 | 本模块新增 |
| id | `uuid4().hex`（32 位） | `randomUUID()`（36 位带连字符） | 均唯一；ICS 的 UID 各自加域名后缀（`@dschat` / `@potato-calendar`） |
| 多租户 | `user_id` + 登录 Cookie | 单机单用户、无鉴权 | 隔离交给主程序；本模块不存 `user_id` |
| API 风格 | `/api/events`，无版本前缀 | `/api/v1/*` | 通过 `/compat/dschat/*` 提供 dschat 2 形状的入口 |
| AI 调用 | 中文标记行（伪工具调用） | 结构化指令对象 | `/commands/markup` 直接吃标记行，转换为同一套指令对象 |

### 8.2 标记行兼容（AI 侧）

dschat 2 的 AI 输出会给用户看这样的行（`server.py` 实际注入 **7 字段**，其 `docs.html` 写的是 8 字段，两者都兼容）：

```
[新增日程] 标题 | 日期 | 开始时间 | 结束时间 | 地点 | 重复 | 重复截止
[删除日程] 标题
[新增待办] 标题 | 优先级 | 截止日期 | 科目
[新增学期] 名称 | 起始日期 | 周数
```

投递到 `POST /commands/markup` 即可一次执行多行，返回逐条结果：

```bash
curl -s localhost:3210/api/v1/commands/markup -H 'Content-Type: application/json' -d '{
  "text": "[新增日程] 每周例会 | 2026-09-20 | 10:00 | 11:00 | 三教101 | 每2周 | 2026-12-31\n[新增待办] 高数作业 | 高 | 2026-09-25 | 数学"
}'
```

```json
{
  "ok": true,
  "succeeded": 2,
  "failed": 0,
  "unparsed": [],
  "drafts": [ { "action": "create", "target": "schedule", "fields": { "title": "每周例会", "repeat": { "type": "weekly", "interval": 2 } } } ],
  "results": [ { "ok": true, "item": { "id": "…" } } ]
}
```

映射要点：

- `无` / 空 → 视为未提供（时刻、重复截止等）；
- 优先级 `高/中/低`（或 `high/medium/low`）→ `2/1/0`；
- 重复 `每2周`、`每周`、`每天` 等中文写法可解析；第 7 列为纯数字时按 8 字段旧格式（重复 + 间隔）解析；
- `[新增学期]` 转成跨天的日历事件（`startDate` = 起始日期，`endDate` = 起始日 + 周数×7 − 1，`category = study`，`tags` 记录周数）；
- `[删除待办]` / `[删除日程]` 转为按关键词匹配的 `delete` 指令。

### 8.3 可以借鉴 / 不能对齐的部分

**可以对齐（已实现）**：日期与时刻字符串格式、宽松中文日期归一化、`repeat` 的五个基础频率 + interval + until、title/date 必填校验、ICS 导出（`GET /ics`）、单日事件的等价语义、AI 标记行入口。

**无法对齐（本模块能力更强或语义不同）**：

- 跨天区间（dschat 2 无）；
- 状态机（dschat 2 的 event 没有状态）；
- 分类与颜色（dschat 2 的 event 完全没有这两个字段，只有 todo 的自由文本「科目」）；
- `count` 型重复与 `weekday` 型重复；
- 提醒；
- API 版本前缀与错误码体系（本模块用 `/api/v1` + `ERROR_CODES`，通过 `/compat/dschat/*` 做兼容而不是改主接口）。

**已知的 dschat 2 侧缺陷（本模块不继承）**：`GET /api/events?start=&end=` 按其原始 `date` 过滤而非 occurrence，循环事件首次日期在范围外时会漏；ICS 全天事件的 `DTEND` 与 `DTSTART` 同一天（不符合 RFC 5545 开区间语义）。

## 9. 思源学堂接入（LMS）

> 目标：把「思源学堂里有什么作业 / 什么时候直播」变成日历里的待办与日程。
> 参考实现：[yan-xiaoo/XJTUToolBox](https://github.com/yan-xiaoo/XJTUToolBox) 的 `lms/` 与 `auth/` 模块（Python）。
> 本模块用**零依赖 Node.js** 重写，只保留只读能力，不代交作业、不改学校数据。

### 9.1 设计原则

| 原则 | 落地方式 |
| --- | --- |
| 只读 | 只调用查询类接口（课程 / 活动 / 详情 / 提交记录），没有任何写学校的动作 |
| 可离线 | 课程与活动落本地缓存（`data/lms-courses.json`、`data/lms-activities.json`），断网也能看上次结果 |
| 先预览后写入 | 同步分两步：`/lms/sync/preview` 只算不写，`/lms/sync/apply` 才落库 |
| 幂等 | 每条同步记录带 `externalId = lms:activity:<学校活动 ID>`，重复同步只更新不新增 |
| 不覆盖用户意志 | 用户勾成「已完成」的作业不会被同步改回未完成，日程的 `reminders` 也保留；注意 `markSubmittedDone`（默认开）会把学堂里已提交的作业标成已完成 |
| 凭据最小化 | 不保存密码；会话票据单独存 `data/lms-session.json`，权限 0600，7 天后自动失效 |

### 9.2 登录：统一身份认证（CAS）状态机

登录链路与学校网页完全一致，拆成可交互的状态机，便于前端一步步引导：

1. `GET https://lms.xjtu.edu.cn` → 302 到 `https://login.xjtu.edu.cn/cas/login?service=…`，页面里带 `execution` 隐藏域；
2. `GET /cas/jwt/publicKey` 取 RSA 公钥，密码用 **RSA/PKCS1v1.5** 加密后加 `__RSA__` 前缀（明文密码不出本机）；
3. `POST /cas/mfa/detect` 探测是否需要两步验证（返回 `state` / `need`）；
4. `POST` 登录表单（带 `execution`、`fpVisitorId`、`mfaState`、`captcha`、`failN` 等字段）；
5. 若服务端要求**安全手机验证**：`GET /cas/{mfa|sec}/initByType/securephone` → `POST /attest/api/guard/securephone/send` → `POST /attest/api/guard/securephone/valid`，随后回到第 4 步；
6. 连续失败 3 次后服务端要求图形验证码：`GET /cas/captcha.jpg`。

登录状态取值：`anonymous`（未登录）/ `need_mfa`（等验证码）/ `need_captcha`（等图形验证码）/ `ready`（已登录）/ `error`（失败或需要人工处理，如账号有多重身份）。

### 9.3 接口清单

前缀 `/api/v1`；未登录访问需要鉴权的接口返回 `401 UNAUTHORIZED`。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/lms/status` | — | 登录状态、用户、MFA 上下文、缓存、同步统计与自动同步设置 |
| POST | `/lms/login` | — | `{ username, password, captcha? }`，返回状态快照 |
| POST | `/lms/mfa/send` | — | 发送短信验证码，返回脱敏手机号 |
| POST | `/lms/mfa/verify` | — | `{ code }`，成功后自动继续登录流程 |
| GET | `/lms/captcha` | — | 图形验证码（`image/jpeg` 二进制，可直接 `<img>`） |
| POST | `/lms/logout` | — | 清除本地会话票据（不影响学校侧） |
| POST | `/lms/settings` | ✅ | `{ autoSync?, autoSyncIntervalHours? }` 开关自动同步（1~168 小时，默认 6 小时） |
| GET | `/lms/courses` | ✅ | 课程列表（`?refresh=1` 强制刷新；有缓存时离线可读，响应带 `loggedIn`） |
| GET | `/lms/activities` | ✅ | 活动列表（`?courseId=&type=&refresh=1`，`type` 取 `homework / material / lesson / lecture_live`，或分组名 `online`（网课 = 直播 + 回放 + 在线视频）） |
| GET | `/lms/activities/:id` | ✅ | 活动详情（含作业说明、提交次数、附件清单） |
| POST | `/lms/sync/preview` | ✅ | 生成同步计划（只读） |
| POST | `/lms/sync/apply` | ✅ | 执行同步，可只同步 `keys` 指定的条目 |

同步参数（preview / apply 通用）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `types` | `['homework','lecture_live']` | 参与同步的活动类型；要导入回放就加 `'lesson'` |
| `courseIds` | 全部 | 只同步指定课程 |
| `includePast` | `false` | 是否包含已经过期/结束的活动 |
| `skipSubmitted` | `true` | 已提交的作业是否跳过 |
| `markSubmittedDone` | `true` | 已提交的作业是否直接标成「已完成」 |
| `includeCourseRange` | `false` | 是否把整学期课程做成一条跨学期的日历事件（**会在月视图每天都出现**，默认关闭） |
| `pruneStale` | `false` | 思源学堂已查不到的活动，是否删掉本地对应记录 |
| `refresh` | `false` | 忽略缓存，强制重新拉取 |
| `keys` | 全部 | 只应用这些 `externalId` |
| `today` | 服务器当天 | 仅测试用，覆盖「今天」以得到确定结果 |

### 9.4 映射规则

| 思源学堂数据 | 落到哪个集合 | 说明 |
| --- | --- | --- |
| 作业 `homework`（同一天两端都有具体时刻） | **日程** `/schedules`（`category=study`） | 有真实起止时刻，是时段安排 |
| 作业 `homework`（其余情况） | **待办** `/todos` | 作业的本质就是「某天要交的一件事」：`deadline=截止日`、`priority`、`completed`（已提交时） |
| 直播 `lecture_live`（有时刻） | **日程** `/schedules`（`category=class`） | 用真实起止时刻 |
| 直播 `lecture_live`（没有时刻） | **全天事件** `/events`（`startDate=endDate`、`allDay=true`） | 日程必须是时段，没有时刻的安排只能是日期粒度事件 |
| 回放 `lesson` | 默认不导入 | 属于历史内容；需要时把 `lesson` 加进 `types`（有时刻→日程，没有→全天事件） |
| 资料 `material` | 不导入 | 没有时间语义 |
| 课程 `course` | 默认不写日历 | 可选项：整学期区间做成一条日历事件 |

**为什么作业不是日程**：日程模型要求 `startTime`（它是「几点到几点做什么」），
而作业只有「哪天交」。旧版本用 `allDay` 把这两件事挤在一个集合里，导致「完成作业」和
「完成一场会议」变成了同一个操作；现在作业进待办，完成态天然成立。

生成的字段细节：

- `title`：`[课程名] 活动标题`（超过 120 字截断）；
- `description`：课程、教师、类型、截止时间、来源活动 ID（多行文本）；
- `tags`：`['思源学堂', '作业'|'直播'|'回放', 课程名]`；
- 待办：`deadline`（作业截止日）、`priority`（距截止 ≤1 天为 2，≤3 天为 1，其余 0）、
  `completed`（已提交且勾选了「标记为完成」时为 `true`；学生自己勾过的状态会被保留）；
  **不写** `category / location / reminders / status / allDay`；
- 日程：`date + startTime(+endTime)`、`category`、`location`、`reminders`（提前 60 分钟，直播 15 分钟）；
- 事件：`startDate = endDate = 日期`、`allDay: true`、`category: study`；
- `source`：`import`；`externalId`：`lms:activity:<活动 ID>`（三个集合共用同一个键，幂等查找会把三个集合一起查）。

### 9.5 幂等与「失效」处理

一次同步计划里每条候选记录都带一个动作：

| 动作 | 含义 | 默认勾选 |
| --- | --- | --- |
| `create` | 本地没有 → 新建 | ✅ |
| `update` | 已有且标题 / 时间 / 分类 / 优先级 / 标签发生变化 → 更新 | ✅ |
| `skip` | 已是最新，或按规则不导入（过期、已提交、类型不参与） | — |
| `stale` | 本地有 `lms:` 记录，但思源学堂已经查不到这条活动 | —（`pruneStale=true` 时删除） |

判定字段按 kind 分别比较（只比「学校给的事实」）：

| kind | 比较字段 |
| --- | --- |
| `todo` | `title / description / deadline / priority / completed` |
| `schedule` | `title / description / category / date / startTime / endTime / priority` |
| `event` | `title / description / category / startDate / endDate` |

外加 `tags`。用户自己改的提醒、地点、预估时长不会被同步覆盖。
`existingByExternalId` 会同时查 `schedules / events / todos` 三个集合，否则作业每次同步都会被重复创建。

### 9.6 给 AI Agent 的工具契约

`GET /ai/capabilities` 的返回里有 `aiTools` 字段（**由各模块声明后自动聚合**，每项带 `module` 标明来源；
思源学堂的定义在 `src/modules/lms/tools.js`，通过 `module.js` 的 `aiTools` 字段暴露），
每个工具都标了 `name / method / path / params / requiresAuth / mutates`，
未来接入模型时只需把这份清单注册成 function-calling 工具即可：登录、查课程、查活动、预览同步、执行同步。

### 9.7 安全与隐私

- **不保存密码**：密码只在内存中存活，用服务端公钥加密后立刻发出；进程重启需要重新登录。
- **会话票据**：`data/lms-session.json`，权限 `0600`，随 `data/*.json` 一起被 `.gitignore` 排除，不会进版本库。
- **只监听本机**：后端仍只绑定 `127.0.0.1`，思源学堂凭据不会离开本机。
- **不信任返回内容**：所有学校返回的文本在写入日历前都按纯文本处理（不解析 HTML 到界面）。

### 9.8 已知限制

- 思源学堂**不提供上课时间/地点**，所以「自动生成课表」需要另外接移动教务（jwapp）的课表接口，本阶段未做。
- 两步验证必须人工输入短信验证码（学校没有提供免验证的 API 通道）。
- 作业是否「已提交」需要逐个活动查详情，单次预览最多补拉 40 条；多余的部分下次预览继续。
- 学校接口字段一旦调整，只需改 `src/modules/lms/api.js` 一个文件（字段归一化都在这里）。

## 10. 记忆（Agent 记忆）

> **记忆本身只有契约**：记忆模块尚未装配，`/memories*` 现在返回 `404 NOT_FOUND`。
> 但**注入通道已经通了**：`GET /ai/context` 已在 `modules/ai/` 实现（见 6.4），
> 现在返回空预算的 `memory`，记忆模块装配后自动生效 —— 调用方不用改一行。
> 先钉死契约，是为了让主程序接 provider 时知道「上下文从哪来、什么能写、写错了谁负责」。
> 这一层不做，Agent 每轮对话都是失忆的，还会反复问同样的问题。

### 10.1 记忆是什么、不是什么

一条**记忆** = 跨会话、可复用、且**不是从别的数据现算出来**的结论。三个条件同时满足才算：

| 条件 | 反例 |
| --- | --- |
| 跨会话（下次依然成立） | 「明天下午三点开会」 |
| 可复用（影响不止一次决策） | 「这条作业今天交」 |
| 非派生（不能从已有集合查出来） | 「这周有 3 条待办」 |

**先选去处，再选接口**（与开头的「★ AI 速查」同一套思路）：

| 用户说的 | 去处 | 接口 |
| --- | --- | --- |
| 「周三下午 6-8 节有课」 | 日程（重复规则） | `POST /schedules` |
| 「下周三下午要去实验室」 | 日程 | `POST /schedules` |
| 「10 月底交大作业」 | 待办 | `POST /todos` |
| 「我周三下午不方便」 | **记忆**（`constraint`） | `POST /memories/propose` |
| 「我在读大二，专业是材料」 | **记忆**（`fact`） | `POST /memories/propose` |
| 「作业总是拖到最后一天」 | **派生查询**（原料在 `data/command-logs.json`） | 不落库 |
| 「提醒我提前 10 分钟」 | 设置默认值 | 不落库 |

三条铁律：

1. **有确切时间位置的一律进日历三域**（事件 / 日程 / 待办）。记忆**不许**存「某天要做某事」——
   同一条信息存两处，必然有一天不一致。
2. **能算出来的不要存**。`data/command-logs.json` 已经在记录你的每条指令；要「你习惯晚上加任务」这类结论，
   应该是一个查询，而不是一条会过期的记忆。
3. **AI 推断的记忆一律不能直接写**：只能提议（`POST /memories/propose`），用户点确认才落库。理由见 10.6。

### 10.2 数据模型 Memory

集合 `memories` → `data/memories.json`（`{ schemaVersion, items: [...] }`，原子写，与其它集合一致）。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 存储层 | 主键 |
| `scope` | string | ✅ | `global` / `course:<课程id>` / `module:<模块id>`，见 10.3 |
| `kind` | enum | ✅ | `fact` / `preference` / `constraint` / `episodic` / `decision` |
| `key` | string \| null | — | 稳定键（`snake_case`）；同 `scope + key` 视为**同一条记忆**，见 10.3 |
| `text` | string | ✅ | 人类可读的完整句，1~200 字，**会直接进提示词** |
| `value` | any \| null | — | 结构化值（可选）。有它时模型更容易稳定复用，如 `{"from":"19:00"}` |
| `source` | enum | ✅ | `user`（用户明说）/ `ai`（模型提议后经确认）/ `import` |
| `sourceRef` | object \| null | — | 从哪学的：`{"logId":"…"}` / `{"messageId":"…"}`。**可追溯才可信任** |
| `confidence` | number | — | 0~1；`source: "user"` 恒为 1 |
| `status` | enum | ✅ | `active` / `superseded` / `archived` / `rejected`，见 10.4 |
| `supersededBy` | string \| null | — | 被哪条取代（保留链，**不删除**） |
| `useCount` | number | 派生 | 命中次数（注入或检索命中都算） |
| `lastUsedAt` | string \| null | 派生 | 最后一次命中时间 |
| `reviewAt` | string \| null | — | 到期待复核（带时效的结论，如「这学期」） |
| `createdAt` / `updatedAt` | string | 存储层 | ISO 8601 |

`kind` 的语义边界（**选错会让注入顺序和界面分组一起错**）：

| kind | 含义 | 例子 | 是否进上下文 |
| --- | --- | --- | --- |
| `fact` | 稳定属性 | 我在读大二；高数老师是王老师 | ✅ |
| `preference` | 影响**怎么做** | 晚上效率高，别排早上 | ✅ |
| `constraint` | 影响**能不能** | 周三下午不方便；实验室周二关门 | ✅ |
| `decision` | 对取舍的拍板 | 不导入已过期作业 | ✅ |
| `episodic` | 一次性经历留下的结论 | 上次数据结构作业拖到最后一天 | ❌ 只检索 |

`text` 的写作规范（它直接进提示词，写坏了就是脏提示词）：

- 写**完整句、主语是用户**：「我习惯晚上 19:00 之后安排学习任务」；
- **不要**把对话抄进来（`用户说了"记住晚上学习"` ❌）、不要写日期、不要以「记住」开头；
- 不用「可能 / 大概 / 也许」——不确定就别记；
- 60 字以内最佳；超过 200 字 → `400`。

### 10.3 作用域与键

`scope` 决定**这条记忆在什么场合被想起来**。没有作用域，记忆一多就是噪音。

| `scope` | 含义 | 注入时机 |
| --- | --- | --- |
| `global` | 与用户本人有关 | 每次都在预算内参与排序 |
| `course:<课程 id>` | 某一门课（id 用 `GET /lms/courses` 里的课程 id，见 9.3） | 当次对话涉及该课程时（`GET /ai/context?courseId=`） |
| `module:<模块 id>` | 某个功能域的使用偏好（如 `module:calendar`） | 当次对话在该视图 / 模块时 |

> `course:` 的 id **不做存在性校验**：课程可能还没同步，也可能来自别的教务源。
> 但请优先用 `/lms/courses` 里真实存在的 id，否则这条记忆永远不会被注入。

`key` 是**去重与覆盖的唯一依据**：小写字母 / 数字 / 下划线，≤ 40 字符，语义化，不要塞中文、不要带 scope 前缀
（scope 已经表达了作用域）。

| 好的 key | 差的 key |
| --- | --- |
| `preferred_study_window` | `习惯`、`key1` |
| `teacher`（在 `scope: course:39020` 下） | `course_39020_teacher`（scope 里已经说了是哪门课） |
| `avoid_morning_schedule` | `avoid_morning_schedule_2026`（带时间 = 永远不会覆盖） |

写入规则：

- **有 `key`**：同 `scope + key` 已有 `active` 条 → 旧条转 `superseded`（`supersededBy` 指向新条），**不删**。
  用户可能改回来，链上留证。
- **无 `key`**：按 `scope + 归一化 text` 去重（归一化 = 去空白与标点、全角转半角）。
  完全相同的重复调用视为幂等：返回既有条 + `"duplicated": true`，**不新建**。

### 10.4 生命周期

```
propose（不落库）
      │ 用户确认
      ▼
   active ──同 scope+key 写入新值──▶ superseded（保留链，可查）
      │
      ├──用户否决──────────▶ rejected（负记忆：AI 不得再提议同 scope+key）
      └──长期未命中────────▶ archived（不删，用户可恢复）
```

| 转换 | 触发者 | 条件 | 可逆 |
| --- | --- | --- | --- |
| → `active` | 用户确认 / 用户明说记住 | — | — |
| `active` → `superseded` | 写入同 `scope + key` | — | 可（再写一条新的） |
| `active` → `rejected` | 用户在确认卡或管理页点否决 | — | **不可逆为 active**，只能新建 |
| `active` → `archived` | 用户手动 / 后续自动策略 | `useCount = 0` 且 90 天未命中（本阶段只手动） | 可恢复 |
| `DELETE` | 用户 | — | 不可逆（同 key 允许重新提议） |

`rejected` 不是废数据，是**负记忆**：AI 提议前必须查同 `scope + key` 是否已被否决
（`GET /memories?scope=&key=`），否则会把同一个已经被否掉的建议反复端上来。

#### POST /memories（显式写入）

```bash
curl -s -X POST localhost:3210/api/v1/memories -H 'Content-Type: application/json' -d '{
  "scope": "global",
  "kind": "constraint",
  "key": "wednesday_afternoon_busy",
  "text": "我周三下午不方便安排学习任务",
  "source": "user",
  "sourceRef": { "messageId": "m-201" }
}'
```

`201` 返回新条；若同 `scope + key` 已有 `active` 条，返回 **`409 CONFLICT`** 而不是静默覆盖：

```json
{
  "ok": false,
  "error": {
    "code": "CONFLICT",
    "message": "已存在同键记忆",
    "details": {
      "existing": { "id": "…", "text": "我周三下午要上课" },
      "hint": "带 \"replace\": true 表示用新值取代旧值（旧条转 superseded，不删除）；否则请让用户确认后重试"
    }
  }
}
```

> 冲突**必须让用户选**（保留旧的 / 换成新的 / 两条都留），调用方不许替用户决定。
> 这是记忆最容易失去信任的地方：一条错的长期偏好会污染后面**每一次**对话，而用户根本不知道它存在。

无 `key` 时按 10.3 的 text 去重，命中即返回 `200 + { "item": {…}, "duplicated": true }`。

**敏感信息直接拒**：`text` 命中身份证 / 学号 + 密码 / 银行卡 / 短信验证码等模式时返回 `400`，
`details.reason = "sensitive_content"`（不新增错误码，见 1.2）。

#### POST /memories/propose（提议，不落库）

**AI 唯一被允许的写入口**（用户明说之外的路径都走这里）。请求体同 `POST /memories`，另可带 `confidence`。

```json
{
  "ok": true,
  "draft": {
    "ok": true,
    "action": "create",
    "target": "memory",
    "fields": {
      "scope": "global",
      "kind": "preference",
      "key": "preferred_study_window",
      "text": "我习惯晚上 19:00 之后安排学习任务",
      "value": { "from": "19:00" }
    },
    "confidence": 0.72,
    "warnings": ["与已有记忆「我习惯下午学习」冲突"],
    "explain": "记下你更习惯晚上学习"
  },
  "conflicts": [{ "id": "91ab…", "scope": "global", "kind": "preference", "text": "我习惯下午学习" }],
  "writes": false
}
```

- `draft` 的形状与 **4.2 的指令对象完全一致**，只是 `target` 取 `"memory"` ——
  前端可以**直接复用草稿确认卡**，不必为记忆另写一套 UI；
- `writes: false` 是明确声明：**这个接口永远不会写库**；
- **记忆复用第 4 章的指令管线**：`"memory"` 也是合法的指令目标，所以「记住 我不喜欢早上排任务」
  既能走 `/commands/parse`（本地规则），也能走 `/commands/markup`（dschat 2 兼容），
  落库仍然走 `/commands/execute`。实现时应在记忆模块里 `registerHandler('memory')`。

#### GET /ai/context（给模型的上下文）

见 10.7。

### 10.6 给 AI 的调用约定（**这一节是硬规则**）

| 场景 | 允许的调用 |
| --- | --- |
| 用户明说「记住… / 以后都… / 别再…」 | `POST /memories`（`source: "user"`），落库后回执一句「记住了：…」并可撤销 |
| AI 自己觉得这句值得记 | **只能** `POST /memories/propose`，等用户确认 |
| 需要历史背景才能回答 | `GET /memories?q=&scope=&kind=episodic` |
| 每轮对话开头 | `GET /ai/context?view=&module=` |

**为什么推断的记忆一律不许直接写**：记忆的错法和待办不一样。一条写错的待办，用户当天就会看见；
而一条写错的**偏好**（比如把「这次不想早上排」记成「用户不喜欢早上」）会静默影响之后**每一次**排期建议，
用户还不知道它存在。所以本版规则是：**推断 → 提议 → 用户点确认**，没有例外。

提议时还要守：

- 一轮对话**最多提议 3 条**（防刷屏）；
- 同 `scope + key` 已是 `active` 且内容等价 → 不提；已 `rejected` → **绝不重提**；
- 只提**用户自己说过**的事，不提推测（「用户可能想考研」❌）；
- 一次性的安排、能从日历 / 待办 / 指令日志查到的事实，都不提（见 10.1）。

### 10.7 上下文注入与检索

**注入（push）**：`GET /ai/context?view=calendar&module=calendar&courseId=39020`（**已实现**，见 6.4）

```json
{
  "ok": true,
  "now": "2026-10-12T09:30:00+08:00",
  "today": "2026-10-12",
  "view": "calendar",
  "module": "calendar",
  "courseId": 39020,
  "memory": {
    "injected": [
      { "id": "2f0c…", "scope": "global", "kind": "preference", "text": "我习惯晚上 19:00 之后安排学习任务" }
    ],
    "budget": { "maxItems": 8, "maxChars": 600, "usedItems": 1, "usedChars": 21, "truncated": false }
  },
  "recent": {
    "todos": { "open": 3, "overdue": 1, "dueToday": 1 },
    "today": { "schedules": 2, "events": 1 }
  }
}
```

> 记忆没装配时 `memory.injected` 为 `[]`、`budget` 照常给出 —— 调用方不需要判断"记忆有没有上线"。

- **排序**：`score = kind 权重 × confidence × 新鲜度`；权重 `constraint 1.0 > preference 0.9 > fact 0.8 > decision 0.6`，
  `episodic` 不注入（只走检索）；新鲜度按 `lastUsedAt ?? updatedAt` 做 90 天半衰期衰减。
- **预算**：默认 ≤ 8 条 / ≤ 600 字。超了先截 `text`（保首句），仍超就按 score 从低到高丢，
  并置 `truncated: true` —— 告诉调用方「还有记忆没进来，需要时自己检索」。
- **命中即回报**：注入的这批自动累加 `useCount` 并刷新 `lastUsedAt`（这是后续淘汰的唯一依据）。

**检索（pull）**：`GET /memories?q=数据结构&scope=course:39020&kind=episodic`。
用在：用户问「你还记得…」、要针对某门课给建议、注入被 `truncated` 时补查。

### 10.8 隐私与可见性

- **只在本机**：`data/memories.json`，与其它集合一样原子写。单机单用户、无鉴权（见第 11 节）。
- **每条都要能追溯到出处**：`sourceRef` 的填写是「尽力而为」，但管理页必须显示它是从哪句话学的。
- **能看、能改、能删、能否决**——不可见的记忆等于不可信的 Agent。管理入口放 **设置 → 记忆**
  （用 `registerSettingsSection` 这个扩展点，不占左栏入口），对话里只留一条「记住了」回执。
- **清空**：整体删除前先备份成 `memories.json.bak-<时间戳>`，沿用存储层对损坏文件的备份习惯。
- 不做跨设备同步；不存敏感信息原文（见 10.5 的拒绝规则）。

（不是 `501` —— 框架只在「已声明但未实现的框架级路由」上返回 501，见 1.2）。
`GET /ai/context` **已经实现**（在 `modules/ai/` 里，见 6.4），它返回的 `memory` 现在恒为空预算。

照 [模块开发指南.md](模块开发指南.md) 落地时的清单：

| 项 | 内容 |
| --- | --- |
| 集合 | `memories`（`data/memories.json`） |
| 服务 | 去重 / 覆盖（superseded 链）/ 冲突检测 / 敏感信息过滤 / 预算与排序 / 命中回报 |
| 路由 | 10.5 的 6 个记忆接口（`/ai/context` 已经有了，别重复注册） |
| 指令 | `registerHandler('memory')` + 中文规则「记住 …」，复用草稿确认卡 |
| 服务钩子 | 暴露 `services.memory.inject({ view, module, courseId, maxItems, maxChars })`，`/ai/context` 会自动调用并把结果放进 `memory` 字段 —— **调用方与前端都不用改** |
| aiTools | `memory_search` / `memory_write` / `memory_forget`（实现后 `/ai/capabilities` 的清单由 **29 → 32**，记得同步更新 6.1 的数字） |
| 前端 | 设置 → 记忆（列表 / 改 / 删 / 清空 / 导出）；对话里的「记住了」回执 |
| 测试 | 幂等、冲突 409、作用域隔离、预算截断、敏感信息拒绝、`rejected` 不重提 |

**本版明确不做**（有意的取舍，不是遗漏）：

- 向量 / embedding 检索：本地零依赖 + 记忆量级（<500 条）下，关键词 + 作用域已经够用；
- 自动淘汰定时任务：先手动 + 计数，等真有数据了再谈；
- 无确认的自动写入（理由见 10.6）；
- 推断记忆的**抽取时机**由主程序决定：建议会话结束或每 N 轮抽一次，
  不要每轮都让模型判断「要不要记」——又贵又吵。

## 11. 已知限制

- 记忆（第 10 节）本阶段**只有契约**：`/memories*` 与 `/ai/context` 未实现，调用返回 404。
- 单机单用户、无鉴权；服务仅绑定 `127.0.0.1`（dschat 2 的 `user_id` 隔离由主程序负责）。
- 跨零点日程需拆成两条；`endTime` 不支持小于 `startTime`。
- 重复日程的单个实例不可单独修改/删除（与 PotatoCalendar 一致；如需支持，需引入例外日 `exceptions` 字段）。
- 聚合查询最长 400 天；未做分页（数据量小，全量内存驻留）。
- ICS 导出不分块折行（长 DESCRIPTION 可能超过 75 字节的建议宽度）；时间输出为浮动本地时间，不含时区。
- 学习记录导入、AI 理解为预留能力（农历已实现：`GET /meta/lunar`，单日 + 批量两种模式）。
- 早期版本写入的「日期锚点」行（`schedules` 里 `allDay: true`）在启动时会被一次性迁成待办；
  `/calendar` 还保留了 `imported` 桶作为兜底（迁移失败时也保证数据可见）。
- 思源学堂的作业现在直接进待办（见 9.4），不再有「同步进来了但待办列表看不见」的问题。
- 思源学堂接入（第 9 节）目前只覆盖课程、作业、直播/回放；**上课时间不在思源学堂**，真正的课表需要另接移动教务，本阶段未做。
